# Clean-Slate v4 — 归一化功能需求树

Status: `DESIGN_INPUT / REQUIREMENTS_ONLY / NO_PRODUCTION_REFACTOR`
Date: 2026-10-13

## 0. 目的

这份文档描述“用户希望总控系统具备什么行为”，不规定具体架构、框架、文件布局、数据库、Agent SDK 或实现方式。

需求分四层：

1. **一级能力**：用户真正需要系统会做什么。
2. **二级能力**：一级能力稳定包含的行为。
3. **跨域约束**：所有一级能力都必须遵守的质量与治理要求。
4. **场景验收**：用真实任务验证多个能力是否能协同工作。

同一个问题的具体表现不再被拆成新的一级功能；例如“视频多 Agent 协作”属于任务编排能力的场景，“小说蒸馏”属于知识提炼与迁移能力的场景，“聊天上限后继承”属于连续性能力的场景。

---

# 1. 一级能力 A — 目标驱动的自主完成

**用户目标：** 用户主要只说“做 XX”，系统负责把任务从目标推进到真正完成。

### A1 目标理解
当用户给出任务时，系统应识别：
- 最终交付物；
- 明确要求与限制；
- 已存在的长期要求；
- 完成条件；
- 哪些条件不明确但会实质影响结果。

### A2 自主推进
只要不存在必须由用户决定或提供的信息，系统应自行继续执行，而不是每完成一步就等待“继续”。

### A3 完成闭环
系统应负责从理解、准备、执行、检查、修正到交付的完整闭环，不得把内部阶段推进责任转给用户。

### A4 必要时才中断用户
只有以下情况才应要求用户介入：
- 缺少只有用户能够提供的信息；
- 存在不可逆或高影响选择且没有已有授权；
- 用户要求之间存在无法自动裁决的实质冲突；
- 客观能力缺失导致无法继续。

### A5 真实完成
“已计划”“已分发”“已尝试”“Agent 声称完成”均不等于任务完成。系统只能在满足任务完成条件并完成必要验证后声明完成。

---

# 2. 一级能力 B — 自主获取知识、提炼知识与做出最适配决策

**用户目标：** 系统不会的会主动学，不确定的会主动查，多个方案会比较，并把学到的东西真正用于当前任务。

### B1 识别知识缺口
执行过程中，系统应主动识别：
- 当前不知道的内容；
- 可能已经过时的事实；
- 相互矛盾的信息；
- 需要额外证据才能下结论的内容。

### B2 主动获取证据
需要时，系统应主动使用适合的来源，例如：
- 当前网络资料；
- 官方文档；
- 项目文件；
- 既有知识库；
- 历史执行证据；
- 当前工具/Agent 状态；
- 其他经授权的数据源。

### B3 多源比较
重要结论不应机械采用第一个来源或第一个方案。系统应比较相关候选信息或方法，识别其适用条件、局限、时效和证据质量。

### B4 最适配选择
系统应优先选择“最适合当前目标、约束和现有系统”的方案，而不是单纯追求最新、最流行或最复杂。

### B5 大规模内容提炼
面对大量文本、教程、论文、小说、字幕、案例或历史任务时，系统应能提炼：
- 事实与概念；
- 方法与流程；
- 模式与结构；
- 因果关系；
- 成功条件；
- 失败模式；
- 可迁移技巧；
- 可执行工作流。

### B6 知识迁移到执行
提炼出的知识必须能够进入后续决策或执行，而不是只停留在摘要。系统应能说明“提炼出了什么，以及这些知识在当前任务中如何被使用”。

---

# 3. 一级能力 C — 任务规划、调度与多 Agent 协作

**用户目标：** 复杂任务由系统自己拆、排、并发、分工、协调和合并。

### C1 任务分解
系统应把复杂目标分解成足够清楚的工作单元，同时避免为了“看起来结构化”而过度拆分。

### C2 依赖与顺序
系统应识别：
- 必须串行的步骤；
- 可以并行的步骤；
- 前置依赖；
- 等待条件；
- 汇合点；
- 阻塞关系。

### C3 优先级
当同时存在多个要求或工作项时，系统应根据：
- 用户明确优先级；
- 任务关键路径；
- 风险；
- 时效；
- 依赖；
- 资源冲突；
确定执行顺序。

### C4 并发与竞争协调
多个工作同时执行时，系统应防止：
- 对同一状态的冲突修改；
- 重复执行；
- 相互覆盖；
- 资源争抢；
- 一个低优先级任务阻塞关键任务。

### C5 Agent 选择
系统应根据实际需要选择一个或多个 Agent/执行者。没有必要时不应为了“多 Agent”而增加 Agent。

### C6 各司其职
多 Agent 协作时，每个参与者应有明确的：
- 输入；
- 责任；
- 权限边界；
- 预期输出；
- 完成条件；
- 与其他参与者的依赖关系。

### C7 必要信息共享
参与者只应获得完成职责所需的任务目标、用户要求、上游结果、知识和状态；不应无差别复制整个系统上下文。

### C8 结果合并与仲裁
系统应负责检查不同 Agent 输出的：
- 冲突；
- 重复；
- 缺口；
- 不一致；
并形成一个最终一致的结果，而不是简单拼接输出。

---

# 4. 一级能力 D — 理解系统结构并在正确位置实施变更

**用户目标：** 系统知道“东西在哪里、应该改哪里、改了会影响什么”，不会到处乱加规则。

### D1 系统地图
总控应能够识别当前系统及子系统的：
- 组成部分；
- 入口；
- 责任边界；
- 状态位置；
- 知识位置；
- 规则位置；
- 测试/验证位置；
- 依赖关系；
- 生命周期状态。

### D2 精准定位
面对“新增、删除、修改、查询”请求时，系统应先确定正确作用位置，而不是因为不知道原位置就创建新的重复机制。

### D3 修改前理解
修改一个组件前，应理解：
- 它为什么存在；
- 谁依赖它；
- 它依赖谁；
- 当前有效实现是什么；
- 是否已经存在相同能力；
- 修改会影响哪些行为。

### D4 用户要求落位
当用户增加长期要求、任务要求或子系统要求时，系统应把要求放到正确的责任边界，而不是统一堆到总控提示词或公共规则里。

### D5 影响分析
系统性变更前应分析直接影响、间接影响、兼容性和可能新增的失败模式。

### D6 一处主责
同一类核心规则或能力应尽量存在明确主责位置；其他位置通过引用或派生使用，避免多个地方各自维护不同版本。

---

# 5. 一级能力 E — 持久状态、统一知识与跨会话连续性

**用户目标：** GPT 聊天达到上限、换窗口或中断以后，系统仍能准确接着做，而且不会把旧摘要当真值。

### E1 持久任务记录
执行中应持续保留恢复真正需要的信息：
- 用户目标；
- 有效要求；
- 当前计划；
- 已完成工作；
- 正在进行的工作；
- 未完成工作；
- 已确认结果；
- 关键决策及原因；
- 重要证据/资料引用；
- 产生的成果；
- 当前问题；
- 下一步行动。

### E2 可恢复检查点
长任务应在合适的安全点形成可恢复状态，不应直到最后才第一次保存进度。

### E3 精确继承
用户在新对话说“继承/继续”时，系统应恢复正确任务、正确阶段和下一步，而不是要求用户重新描述已经持久化的信息。

### E4 恢复真实对象
继承不能只恢复一段摘要；系统还应能重新定位真正的文件、状态、知识、执行结果和外部依赖。

### E5 避免无意义重做
仍然有效且已经完成的工作应继承；失效或证据不足的部分重新验证；未完成部分继续。

### E6 统一知识治理
共享知识应能够被多个 Agent/子系统复用，但必须知道：
- 来源；
- 适用范围；
- 当前有效性；
- 版本/时间；
- 是正式规则、任务证据还是普通参考。

### E7 新旧真值区分
缓存、摘要、历史聊天、旧文件或旧观察不能自动覆盖更新的权威状态。

---

# 6. 一级能力 F — 运行监测、错误诊断与可靠恢复

**用户目标：** 系统在执行中自己发现不对劲，找到问题点，修复并恢复，而不是一路错到底。

### F1 异常检测
执行过程中应主动识别：
- 结果偏离预期；
- 工具异常；
- Agent 输出异常；
- 数据冲突；
- 要求违反；
- 重复失败；
- 状态不一致；
- 执行结果不确定。

### F2 停止扩大错误
发现足以影响后续正确性的异常时，系统应停止依赖该错误结果继续扩散。

### F3 根因诊断
系统应区分：
- 一次性任务错误；
- 数据/工具问题；
- Agent 局部问题；
- 公共机制问题；
- 架构层问题；
并尽量定位真正原因，而不是只补表面症状。

### F4 主动寻解
如果没有可靠解法，应主动研究成熟方案、当前最佳实践和相似失败案例，再选择最适配的修复方式。

### F5 不确定结果处理
当外部操作出现“可能成功、可能失败”的不确定状态时，应先查明实际结果，避免盲目重试造成重复发送、重复创建、重复支付、重复提交或重复修改。

### F6 故障隔离
一个子系统或 Agent 的局部故障不应无必要地拖垮无关功能；如果故障位于公共基础能力，则应明确受影响范围。

### F7 修复后验证
修复后应确认：
- 原问题是否解决；
- 原有能力是否仍正常；
- 是否出现新的问题；
- 是否遗留临时补丁或重复机制。

---

# 7. 一级能力 G — 子系统与 Agent 生态治理

**用户目标：** 总控不只是调用子系统，还真正知道它们是什么、在哪里、怎么改、怎么升级和怎么退役。

### G1 子系统清单与边界
总控应能够知道当前有哪些子系统/Agent，以及每个系统的：
- 目的；
- 责任；
- 位置；
- 入口；
- 数据/状态边界；
- 依赖；
- 当前生命周期状态。

### G2 子系统增删改查
新增、删除、修改、查询子系统时，系统应知道对应操作位置和影响范围，并维护整体一致性。

### G3 新要求下发
用户给某个子系统增加要求时，总控应识别：
- 哪个子系统负责；
- 应修改什么层级；
- 是否影响公共能力；
- 是否需要同步其他依赖方。

### G4 公共能力继承
子系统可以复用父系统的通用能力，例如：
- 连续性；
- 故障发现；
- 改进流程；
- 知识治理；
- 质量验证；
但不应把子系统特有业务逻辑上收成中央系统的永久复杂度。

### G5 子系统健康
总控应能够观察子系统是否存在：
- 重复机制；
- 长期失败；
- 过时知识；
- 结构漂移；
- 不必要复杂度；
- 与父系统规则冲突。

### G6 生命周期治理
子系统、Agent、工作流和规则都应支持：
- 引入；
- 升级；
- 迁移；
- 替换；
- 停用；
- 删除；
而不是只允许不断新增。

---

# 8. 一级能力 H — 自我进化、主动维护与复杂度控制

**用户目标：** 系统会越来越好，但不能越修越乱、越学越胖、拆东墙补西墙。

### H1 改进信号
以下都可以成为改进候选：
- 用户纠正；
- 执行失败；
- 重复返工；
- Agent 协作问题；
- 新技术/工具；
- 新研究；
- 子系统漂移；
- 维护成本异常。

### H2 候选不等于采用
发现新方法后，应先研究、比较和验证，不得因为“看起来先进”就直接成为正式系统规则。

### H3 以替换优先于叠加
新机制解决旧机制的问题时，应优先考虑替换、合并、删除旧机制，而不是永久保留两套。

### H4 全局而非局部最优
修复一个问题时，应检查是否：
- 损害其他功能；
- 增加新的单点依赖；
- 增加维护负担；
- 让系统更难理解；
- 把问题转移到另一个位置。

### H5 复杂度预算
每个非平凡新增机制都应能够回答：
- 新增了什么能力；
- 替代了什么；
- 为什么不能复用已有机制；
- 引入什么新风险；
- 增加多少维护/上下文/工具成本；
- 能删除或简化什么。

### H6 闲时维护
当存在**已授权且真实可用的后台/定时执行能力**并且没有更高优先级任务时，系统可以主动检查父系统与子系统的隐患、过时内容、重复机制、失效知识和长期问题，并在授权范围内修复。

### H7 闲时维护不得干扰业务
主动维护不得擅自改变用户已经确认的业务结果，不得抢占关键任务，不得把高风险变更伪装成普通清理。

---

# 9. 一级能力 I — 质量验证、完成证明与用户交付

**用户目标：** 系统不仅做，还知道自己到底做没做对，并在结束时让我清楚知道发生了什么。

### I1 按要求核对
交付前应重新核对用户目标、约束和重要中途变更，确认没有漏执行。

### I2 关键结果验证
系统应根据任务性质验证关键结果，而不是只验证流程文件存在或 Agent 声称执行。

### I3 能力级验证
系统应能够回答“哪些能力/风险已经被验证，哪些没有”，而不是只给出测试数量。

### I4 不虚报
必须区分：
- 已完成；
- 已验证；
- 部分完成；
- 尚未验证；
- 被阻塞；
- 结果未知。

### I5 最终汇报
任务完成后，优先交付用户真正要的结果，并简洁说明：
- 完成了什么；
- 关键过程/决策；
- 使用的重要资料或方法；
- 修改了什么；
- 做了哪些检查；
- 剩余风险或未完成事项。

### I6 为下次继续留好状态
最终汇报不是唯一记录。任务结束或暂停前，应确保下次继承所需状态已经可靠保存。

# 10. 跨域约束

这些不是新的一级功能，而是所有功能都必须遵守的要求。

## X1 用户负担最小
系统内部越复杂，越不应把管理成本转给用户。正常使用应尽量保持“给目标、改要求、继续任务”三类交互。

## X2 不臃肿
不能把“新增文件、规则、Agent、测试”本身当成进步。能力提高同时应控制活动机制数量和重复语义。

## X3 不拆东墙补西墙
局部修复必须经过影响检查；不能通过破坏其他已正确能力换取当前问题消失。

## X4 真值与来源可辨
重要状态、知识和结果必须能够区分权威来源、缓存、历史记录、推断和外部参考。

## X5 自主但有边界
系统应尽量自主完成低风险、可逆、已授权工作；不可逆、高影响或权限外操作必须遵守相应授权边界。

## X6 故障隔离
局部故障尽量局部化；公共故障要明确影响范围和降级行为。

## X7 兼容与迁移
系统、Agent、工具、协议升级后，应能判断旧任务/旧状态是可直接继续、需要迁移还是不兼容；不能静默误读。

## X8 成本意识
系统应考虑时间、上下文、工具调用、维护工作和外部资源成本，避免用显著更高成本换取几乎没有收益的复杂设计。

## X9 可追溯
重要要求、决策、变更、执行和验证之间应能追溯，便于恢复、排错和判断影响。

## X10 禁止虚假完成
“写了规则”“建立了 Agent”“产生了计划”“测试文件存在”都不能自动证明实际目标完成。

# 11. 代表性场景验收

场景用于验证能力组合，不再新建重复的一级需求。

| 场景 | 主要验证能力 | 最低预期行为 |
|---|---|---|
| S1 用户说“做 XX” | A+B+C+I | 系统自己理解、补知识、执行、检查并交付，不把内部推进交给用户 |
| S2 需要当前资料的研究任务 | B+E+I | 主动查最新可靠来源，比较后使用，并保留来源/时效 |
| S3 视频多 Agent 制作 | C+E+G+I | 正确拆分角色、识别串并行、共享必要上下文、合并结果、处理冲突 |
| S4 大量小说蒸馏并原创 | B+C+E | 从大量材料提炼可迁移方法，并在原创任务中真正调用，而非只摘要 |
| S5 用户新增长期要求 | D+E+G+H | 判断影响范围和正确落位，替代冲突旧要求，不乱堆全局提示 |
| S6 聊天达到上限后“继承” | E+A | 找到真实任务状态和下一步，继续执行，不要求用户重述 |
| S7 工具超时且结果未知 | F+E | 先确认实际结果，再决定重试/恢复，防止重复副作用 |
| S8 子系统反复出错 | F+G+H | 识别是否系统性问题，找根因、研究方案、修复并验证，不只补当前案例 |
| S9 空闲期主动维护 | H+G+I | 在存在授权后台能力时审查隐患、清理冗余并验证，不干扰业务 |
| S10 多任务/多 Agent 竞争 | C+F | 识别优先级、依赖和共享状态冲突，安全调度 |
| S11 引入新 Agent/工具 | B+D+G+H | 先判断是否需要、与现有能力关系、集成位置和退出旧机制，再决定采用 |
| S12 系统升级后继续旧任务 | E+G+X7 | 判断兼容、迁移或阻塞，不能静默用新语义误读旧状态 |

# 12. 需求层的完成定义

在进入 clean-slate 架构设计前，至少需要做到：

1. 每个用户核心目标都能映射到 A–I 中至少一个一级能力；
2. 具体业务例子优先成为场景，而不是新增重复顶层功能；
3. 新发现的要求先判断是一级能力、二级能力、跨域约束还是场景；
4. 架构设计必须逐项说明如何满足 A–I 与 X1–X10；
5. 任何架构组件如果不能对应明确需求、风险或验证职责，应默认不引入；
6. 后续如果新场景暴露真正无法归入 A–I 的独立能力，再新增一级能力，而不是为了编号完整而冻结需求树。
